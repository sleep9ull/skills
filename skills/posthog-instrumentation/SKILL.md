# PostHog 埋点补充与维护

以已经实现的功能代码、协议代码和真实调用链为依据，补充与维护 PostHog 事件和属性。功能刚开发完成时首次补埋点、功能调整后同步埋点、现有埋点审计与清理，都执行本流程。

先理解功能实际做了什么，再决定采集什么；协议用于核对字段、值域和交互约定，不能仅凭协议声明推断功能可达或业务成功。不借埋点开发或修复功能。

## 最高优先原则：功能实现保持原样

**不允许调整功能源码、实现逻辑、业务接口，仅针对 PostHog 相关内容调整。**

允许改动的内容：PostHog 事件/属性定义、现有 capture 调用与挂点、专用 tracking helper/context/observer、埋点测试、行为场景和契约文档。在混合业务文件里只增删或替换埋点语句、埋点专用局部值和观察挂点；原有业务语句与执行顺序保持原样。

禁止为埋点修改业务方法的参数、返回值、回调或异步/异常约定；禁止调整网络请求、业务状态、数据模型及持久化 schema、导航/路由接口、UI 行为、权限判断、缓存、重试、并发、错误处理或成功/失败分支。默认参数和“行为等价重构”也属于接口/源码调整。不能顺便修复模拟实现、历史 bug 或架构问题。

检查一个辅助对象是否属于 analytics：删除它及其调用后，原功能应以原接口、原控制流正常运行；其输出只能用于统计，不能被业务判断消费。详细判定及拒绝越界实例见 [references/change-boundary.md](references/change-boundary.md)。

**现有信号不足时，完成能准确采集的部分，并列出缺口。** 不增设业务回调，不猜测成功，不以完善漏斗为由扩大范围。这个限制不是默认请求用户放宽边界的理由。

## 执行流程

### 1. 确认目标与基线

从请求和当前会话提取：目标仓库、已实现的代码/协议/页面/功能、待解决的数据问题、排除范围、只审计还是实施。首次补充时盘点完整行为；功能发生调整时对照本次代码差异与旧埋点契约。能从代码确认的信息不要重复询问；真正影响语义且无法推断的选择才问用户。

读取目标仓库规则、相关文档索引、功能源码、现有测试和 tracking 约定。按需定位事件定义、capture 封装、身份管理、共享渠道分发、测试和构建入口，先确认路径在当前分支存在。

记录当前分支、实际 PR base、起始工作区和用户已有改动。只读研究其他 PR/session 的结论，把它们当线索，核对当前文件及实际 diff。区分已合并代码、未推送修正、开放 PR 的提案；不要为了阅读把其他分支合进来。

### 2. 从已有行为盘点埋点

沿目标项目的 UI/入口 → 业务处理 → 数据访问 → 结果/通知追踪实际链路，包括共享组件和其他入口。列出用户能到达的动作、页面/面板、异步结果、空态、失败及取消。查看谁真正写入完成态，别从方法名或状态枚举猜测。

搜索对应事件定义、全部调用点、属性拼装、全局合并、person 属性及下游分析引用。标记重复上报、无调用定义、失效挂点、来源丢失、统计口径漂移和范围交叉。

为每个候选给出 `新增 / 调整 / 清理 / 保留 / 无法准确观测` 的决定，附源码证据。不要为每个按钮机械新增事件；能用已有事件加明确属性表达时优先复用，且避免改变其他入口的语义。

### 3. 先形成差异契约

使用下列紧凑表格，在目标功能现有规格/契约位置维护；不要复制整个全局埋点表：

| 决定 | 事件/属性 | 现有含义 → 目标含义 | 挂点和真实信号 | 属性类型/取值 | 去重及关联范围 | 兼容/影响 | 验证 |
|---|---|---|---|---|---|---|---|

明确 event property、person property、全局 property 的区别。为每个事件注明：

- 点击/展示/提交/结果中的哪一个事实；失败、取消、无变化和未知如何处理。
- 必需与可选属性、类型、单位、索引基数、来源值域；未知时省略还是用约定 unknown。不要把未知 count 记成 0。
- `source`、`surface`、`entry_source` 各自语义，以及父内容、条目、位置、会话等上下文如何贯穿已有链路。
- 一次性、每次页面进入、每个操作或每次满足可见阈值的去重边界；是否需要 operation/session ID。
- 老名称/类型/值域是否兼容；语义变化是否需要版本、新事件或下游迁移说明。

仅有 UI 内存赋值就写明 memory；仅发起外部分享就写明 handoff/request。“请求被调用”不足以表示分享发布、删除账号、文件写入或交易成功。

### 4. 行为场景 → 失败测试 → 最小实现

遵守目标仓库的测试流程，先定义埋点行为场景，再写失败测试；仓库要求 YAML 时先补 YAML。先观察失败原因，再改埋点，通过后只重构埋点部分。

用可注入 capture、时间和只读账号信息测试专用 tracking 对象；复用已有测试 seam。不要为了测试新增业务接口。原有 seam 不足时，将单元可测逻辑放在 analytics helper，并明确集成挂点仍需验证。

实施时：

- 优先复用仓库已有的 typed event/key API、专用值域和 capture 封装，不绕过统一入口直接调用 SDK。仓库无统一入口时，新增封装只服务 PostHog，不改业务接口。
- 在原有动作/响应/通知处旁路采集，不替换、移动、包装业务操作，不新增业务调用；analytics 的 guard 只作用于 analytics，不能提前返回或跳过功能代码。
- 所有关联、计时、去重、账号隔离状态属于 analytics 自己。需要跨启动时独立命名存储，不能扩充业务 session/model schema，也不能改变其清理顺序。
- 异步结果按真实业务信号判定，检查操作发起时的账号与完成时账号。注销后身份是否重置需核实，不为保留旧身份调整 logout 流程。
- 页面曝光由真实进入/可见生命周期触发，不放在页面模型或控制器构造时；保活 Tab、覆盖层、返回、重建要分别核对。
- 曝光阈值、计时、遮挡、后台和去重须先定义，不能用组件挂载、图片下载或预加载替代真实曝光。详细检查见 [references/measurement-patterns.md](references/measurement-patterns.md)。
- 排除范围也要覆盖共享事件、属性合并和导航切换，不只按文件目录排除模块。

### 5. 调整与清理要成套收口

新增：定义 → 属性/值域 → helper → 挂点 → 测试 → 契约，检查每一环。

调整：搜索旧事件值、类型成员、所有 source 分支和 helper；确认其他入口没有被连带修改，检查合并属性覆盖顺序与缺省/legacy context 路径。只修本次目标。

清理：证明挂点失效或事件被替代，移除对应采集及仅被它使用的 tracking 状态/测试/定义。定义仍被其他合法调用、共享渠道或兼容路径使用时保留；不能因局部无调用就删全局 key。不要删除业务回调、功能组件或历史 PostHog 数据。记录停止发送时间/版本、替代关系和查询兼容影响。

全局 SDK 配置、identify 策略和公共属性默认不在局部功能埋点范围内；只有本次明确的 PostHog 需求才调整相应内容。检查共享 capture 是否分发到其他 analytics 渠道。PostHog 调整不能修改它们的白名单、映射、载荷或发送次数。若共用事件导致不可避免的渠道变化，使用已有 PostHog 专用 seam；没有合适 seam 就标记受阻，不改其他渠道。

### 6. 验证语义与“仅埋点”边界

执行最小相关测试、适用的场景校验和 lint/build。使用目标仓库规定的入口，提交前完成其要求的检查。

逐 hunk 与开始时记录的实际 base 比较，不能只看文件名：

- 原业务签名、业务语句顺序、请求次数/入参、返回值、分支、状态写入、持久化和 UI 副作用无变化。
- mixed 文件只出现能解释的 tracking 变化，没有“顺便修复”。已有用户改动与本次改动分清。
- 事件只在正确事实发生时发送；失败/取消/未知/重复回调/账号切换不会产生虚假的成功。
- 同一 ID 在不同 surface 的归因、不同入口、缺省/legacy context、列表位置和共享组件没有串线。
- 新旧事件无重复计数，属性类型不漂移，排除模块及其他 analytics 渠道无变化。

有条件运行真实页面并检查事件载荷；没有条件就明确写未验收。语法检查、独立 harness、带桩类型检查、宿主测试、实际运行和 PostHog 接收是不同证据等级，不能相互冒充。依赖阻塞不允许用“全部验证通过”收尾。

若需要处理冲突，对照双方埋点契约和实际 PR base，重新验证上下文归因、重复定义、共享 helper 和旧路径；禁止用重写功能逻辑解决埋点冲突。未授权时不提交、不推送、不合并 PR。

### 7. 同步与交付

默认交付代码、埋点测试、局部差异契约及验证结果。不默认修改外部埋点表、PostHog taxonomy/dashboard/生产配置或删除远端数据。用户明确要求同步时，先读目标 schema 与当前记录，按最终代码最小更新并回读核验；区分代码完成和实际接收验收状态。

最终说明：

1. 实际新增/调整/清理/保留了什么，事件与关键属性如何变化。
2. 真实挂点、兼容边界、不能准确观测的缺口及排除范围。
3. 仅埋点 diff 自审结论；测试结果、构建/实际运行/PostHog 接收的未验证项。
4. 代码/契约位置；若已有授权发布，附实际 commit/PR/表格同步结果。

不要承诺无法从现有实现证明的业务成功，也不要为补齐统计去改功能。

维护本 skill 时，用 [references/evaluation-cases.json](references/evaluation-cases.json) 的三个隔离场景回归边界、曝光及清理规则；它们是 skill 评测输入，不能代替目标项目的集成测试。验证范围和局限见 [references/evaluation-notes.md](references/evaluation-notes.md)。
